# Стабильные группы глубины в кэше порядка

На общем плане ETL 10к/10к с включённым Live и выключенной миникартой p95 отрисовки после смены статуса снизился со 152,3 до 58,8 мс. За те же 80 обновлений в браузере стало 0 интервалов дольше 100 мс вместо 48. При приближении к одному pipeline эффект сохранился. Порог 16,7 мс всё ещё превышает каждая отрисовка с изменившимися статусами.

## ETL в Storybook

| Вид и продолжительность на версию | p95 CPU draw после тика, мс | p95 худшего интервала rAF на тик, мс | Интервалы rAF > 100 мс | Максимальный интервал rAF, мс |
| --- | ---: | ---: | ---: | ---: |
| Весь граф, 40 с, 80 тиков | 152,3 → 58,8 | 158,3 → 59,3 | 48 / 3 940 → 0 / 4 524 | 250,0 → 66,6 |
| One pipeline, 30 с, 60 тиков | 130,6 → 57,0 | 133,1 → 58,2 | 31 / 3 050 → 0 / 3 384 | 141,9 → 66,7 |

На общем плане осталось 80 интервалов дольше 16,7 мс (был 81), в One pipeline — 60 (было 60). Эта граница отличает сокращение длинных остановок от стабильной отрисовки каждого обновления за кадр. p95 всех интервалов на общем плане составил 9,3 мс у обеих версий за счёт кадров между тиками.

Измерения сделаны на Apple M3 Pro, Chromium 145.0.7632.6 с ANGLE Metal, DPR 2, окно 1600 × 1000 CSS-пикселей, область графа 1600 × 965. Для каждого вида порядок двух зафиксированных сборок был A/B/B/A. Каждое окно открывалось в новом браузере. Обычный таймер Storybook каждые 500 мс менял десять стадий и статусы соседних связей. Обе версии начинали с одинакового состояния. По завершении каждого окна совпали счётчики статусов блоков и хэш пар id/status всех связей. Во всех запусках был один активный WebGL-контекст. На общем плане масштаб 0,0251 ниже порога анимации, в One pipeline при масштабе 0,606 эффекты активны.

Для каждого тика найден один вызов draw, в котором обновились данные сцены. p95 посчитан по всем таким вызовам для двух окон вместе. Пауза — разница соседних временных меток requestAnimationFrame, строго больше 100 мс. Для p95 худшего интервала на тик взят максимальный интервал, пересекающий работу самого тика или его отрисовки. Измерения не включают задержку вывода готового пикселя на дисплей.

Продолжение с адресным пересчётом для тех же сценариев и независимой проверкой изображения доступно в [замерах локальных обновлений Live](2026-11-18-local-live-regions.md).

## Откуда выигрыш

Раньше начало группы блоков в кэше зависело от числа полупрозрачных связей в предыдущей группе. Теперь в ключ входят устойчивая метка группы глубины и локальный уровень перекрытия. Соседние группы оставляют между своими метками свободное место. Поэтому обычная вставка промежуточной группы при выборе элемента сохраняет метки уже существующих групп. Исчерпание свободного промежутка допускает перенумерацию с точным списком изменившихся элементов. Физическая сортировка плотных буферов использует компактные номера, чтобы при равном уровне точно учитывать порядок отдельных примитивов. Изменения ограничены внутренним кэшем. [Вычисление меток](../../../packages/graph/src/lib/scene/webgl/overlapLevels.ts) · [Подготовка порядка](../../../packages/graph/src/lib/scene/webgl/translucentOrder.ts)

| --- | ---: | ---: |

| p95 подготовки видимых диапазонов, мс | 22,1 | 24,8 |

На всех 32 тиках совпало число частей плана. Остались отдельные полные чтения одного или двух источников. В чистой серии p95 объёма загрузки на обновление общего плана составил прежние 2 671 300 байт. В тех же 32 отрисовках подготовка порядка и фильтрация видимых диапазонов вместе заняли 76,3% времени CPU внутри draw. Даже на семи тиках без полных чтений средняя отрисовка занимала 39,1 мс. Следующий участок для оптимизации — повторная обработка уже упорядоченных и видимых диапазонов после локальной смены статуса.

## Nirvana Max

Проверили общий план графа из 13 916 блоков и 18 604 связей на исходном и изменённом WebGL-рендерере, с выключенной миникартой. Две серии редактирования шли в противоположном порядке A/B/B/A и B/A/A/B. На каждый сценарий пришлось по 96 действий на версию. Первое изменение очередной связи на прогретой странице и первый ввод сразу после открытия графа измерялись отдельно.

| Переподключение на прогретой странице | p95 CPU draw, мс | Отрисовки > 16,7 мс | Действия с интервалом rAF > 16,7 мс | Паузы > 100 мс |
| --- | ---: | ---: | ---: | ---: |
| Разные связи, 96 действий | 20,2 → 19,3 | 7 → 8 | 3 → 7 | 0 → 0 |
| Повторно одна связь, 96 действий | 12,3 → 16,6 | 0 → 4 | 6 → 7 | 0 → 0 |

Для повторного переподключения p95 вырос в каждой серии отдельно (12,7 → 17,0 и 10,7 → 15,9 мс). В отдельной трассировке 48 действий на двух сборках не было ни одного вычисления новых меток или локальных уровней. Порядок, его части и версия кэша оставались прежними. Вход в orderTranslucent и проверка версии занимали до 0,1 мс. p95 подготовки смешанного прохода для повторной правки составил 6,4 → 6,3 мс. Причина разницы полных времён повторной правки остаётся открытой.

Для холодного первого ввода открыли по 24 новых браузера на версию. Каждые четыре открытия меняли последовательность A/B/B/A на B/A/A/B. Вызывали первое переподключение одной и той же связи после исходного fit, без предварительного редактирования. Совпали порты, конечная геометрия и загрузка данных (1 271 732 байта на действие). p95 draw был 30,2 → 30,8 мс, p95 от ввода до rAF — 43,0 → 44,3 мс. В обеих версиях не было пауз дольше 100 мс. Бюджет 16,7 мс по CPU превышен в 17 → 19 из 24 отрисовок.

На круговом pan и на zoom через границы детализации сравнили по 240 поз на версию и движение. CPU p95 составил 1,7 → 1,6 мс на pan и 4,7 → 5,0 мс на zoom. В полном наборе интервалы rAF дольше 16,7 мс встретились на 63 → 67 позах pan и 23 → 41 позе zoom. Обратная серия дала 22 → 21 и 4 → 4 соответственно. Во всех сериях пропусков свыше 100 мс и повторных загрузок геометрии было ноль. В диагностическом проходе ни одна из 240 поз не изменила кэш порядка. Каждую следующую позу задавали из rAF, поэтому интервалы включают ожидание следующего браузерного кадра.

Аппаратный таймер WebGL в отдельном проходе показал ограничение общего плана на GPU у обеих версий. При zoom на масштабе меньше 0,04 во всех 23 из 23 поз GPU потратил более 16,7 мс, медиана 23,71 → 23,20 мс. На масштабе от 0,25 в обеих версиях каждая из 21 позы уложилась в 16,7 мс (медианы 3,85 → 3,99 мс). Это другой участок работы, чем подготовка изменившихся статусов в ETL.

## Порядок и изображение

На ETL 10к/10к сравнили 32 последовательных изменения статусов и переходы между видами, изменение глубины двух перекрывающихся блоков, выбор нижнего блока и группы из восьми связей. В 43 состояниях симуляции и 15 состояниях отдельной проверки выбора совпали RGBA при фиксированном времени, последовательность физических диапазонов и вызовы отрисовки WebGL. Проверка убеждалась, что выбор действительно меняет верхний блок, а группа выделения появляется между существующими группами и удаляется при снятии выделения.

В общей проверке ETL и Nirvana совпали 104 из 104 кадров (657 536 000 пикселей, ноль отличающихся каналов), а также проверяемые параметры HTML-карточек. Покрыты переподключения на разных участках графа, выделение, движение и переходы LOD. Для 24 первых и 24 повторных переподключений Nirvana совпали и активные адреса в GPU-буфере, и границы команд.

Тест последовательности из 120 комбинаций изменения статуса, перемещения и смены глубины сравнивает команды инкрементального кэша с полной сортировкой свежих уровней. Отдельно проверены вставка и удаление промежуточной группы, временно скрытые владельцы с сохранённой геометрией, плотная сортировка при широком диапазоне шагов и исчерпание промежутка для новых меток. [Регрессионные тесты](../../../packages/graph/src/lib/scene/webgl/overlapLevels.test.ts)

Проверка текущей сборки прошла для всех пакетов и приложений TypeScript, 2 044 модульных тестов библиотеки и 129 сценариев Chromium/Metal. В модульном наборе остаются шесть ранее помеченных todo. Браузерный набор включает делегированные порты, редактирование связей, эффекты, hit-test и переходы между уровнями детализации.

## Воспроизведение

Архив представляет собой сжатый JSON. В нём находятся интервалы rAF и draw по каждому прогону, контрольные суммы изображений и порядка, поканальные результаты сравнения, сценарии браузера и точный diff между проверенными версиями в sourceChanges. Обе версии включают локальные изменения поверх 89b4f09c. Для восстановления A на копии проверенного дерева B сверь SHA-256 каждого файла с полем after, примени соответствующие diff в обратную сторону и сверь с before. В storybookHAR сохранены контрольные суммы. Сами HTTP-архивы записываются при воспроизведении. Для повтора ETL извлеки сценарий следующей командой, укажи свой путь к worktree в переменной root и запусти Storybook на порту 6017. Сначала запиши base на исходной сборке, затем собери изменённую библиотеку, дождись её появления в Storybook и запиши final. Команды с PIN используют эти сохранённые версии. [Сырые данные](2026-11-18-stable-depth-order.json.gz)

```sh
gzip -dc 2026-11-18-stable-depth-order.json.gz | jq -r '.harness["measure.cjs"]' > measure.cjs
SAVE_BUNDLE=yes node measure.cjs base-freeze,on,fit,2
SAVE_BUNDLE=yes node measure.cjs final-freeze,on,fit,2
PIN=yes node measure.cjs base-fit2,on,fit,20 base-pipeline2,on,pipeline,15 final-fit1,on,fit,20 final-pipeline1,on,pipeline,15 final-fit2,on,fit,20 final-pipeline2,on,pipeline,15 base-fit3,on,fit,20 base-pipeline3,on,pipeline,15
PIN=yes node measure.cjs base-plan,plan,fit,16 final-plan,plan,fit,16
```

Для Nirvana использован NirvanaMaxGraphTest.render исходного Storybook с одинаковым графом в обеих версиях. Точное содержимое nirvana-fixture.json хранится в hardwareControls.fixtureJson, сценарии сборки и прогонов — в hardwareControls.harnesses. После извлечения сценариев и настройки локального пути к worktree собери две версии через build.cjs с именами productionX и depthFinal. depth-cold-abba.py --run воспроизводит серию первых правок.
